    What this costs, regardless of placement

    AVRoutePickerView is UIKit — there is no SwiftUI equivalent on any current SDK, so every variant here needs a UIViewRepresentable. CLAUDE.md says avoid UIKit unless requested, so this is an explicit exception to sign off on, not an implementation detail to bury. 

    // Shared/PlayerHeaderView — needs #if os(iOS) / #if os(macOS) branches;
// AVRoutePickerView does not exist on tvOS or watchOS.
struct RoutePickerButton: UIViewRepresentable {
    var tint: Color
    var activeTint: Color

    func makeUIView(context: Context) -> AVRoutePickerView {
        let view = AVRoutePickerView()
        view.prioritizesVideoDevices = false
        view.accessibilityIdentifier = "airPlayRouteButton"
        return view
    }

    func updateUIView(_ view: AVRoutePickerView, context: Context) {
        view.tintColor = UIColor(tint)
        view.activeTintColor = UIColor(activeTint)   // the "connected" state, for free
    }
}

    Theming risk. PlaybackControlsView applies .brightness(-appearance.playbackDarkness), .opacity(appearance.playbackAlpha) and .blendMode(appearance.playbackBlendMode) from WallpaperTheme. Those composite a representable, but a system-drawn glyph under a non-normal blend mode is exactly the thing that looks right in one wallpaper theme and wrong in another. Tints can be synced from appearance.accentColor; the blend mode needs a real visual pass across themes.

    Don't gate on route availability. AVRouteDetector.multipleRoutesDetected would let the button hide when no targets exist. Resist it — a control that appears and vanishes is worse for discoverability than one that is always present, and route detection triggers active network discovery, so it would also need scoping to the header's visible lifetime to avoid a background power drain.

    macOS gap. AudioPlayerController.outputLatency is #if os(iOS) || os(tvOS) and returns 0 otherwise — so on the in-flight native macOS target the visualizer has no AirPlay latency compensation to begin with.
